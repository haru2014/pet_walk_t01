# 편안하개 홈 화면 ‘바로 산책 시작하기’ 자유 산책 기능 구현 지시서

## 1. 목적

현재 홈 화면의 **‘바로 산책 시작하기’**를 경로 추천 기능과 분리하여, 사용자가 사전에 추천 경로를 선택하지 않고도 원하는 방향으로 산책할 수 있으며, 산책 중 실제 GPS 이동 경로와 산책 정보를 기록하는 **자유 산책 기능**으로 개선한다.

기존의 **산책 경로 추천 기능은 유지**한다. 두 기능은 사용 목적과 데이터 흐름을 명확히 구분한다.

- **바로 산책 시작하기:** 경로를 미리 생성하거나 선택하지 않고 산책을 시작하고 실제 이동 경로를 기록한다.
- **산책 경로 추천받기:** 공원·출발 위치·희망 시간 또는 거리 등의 조건으로 추천 경로를 생성하고, 사용자가 선택한 경로를 참고해 산책한다.

> 핵심 원칙: 경로 추천은 선택 기능이며, GPS 기록은 실제 산책을 기록하는 기능이다. 추천 경로와 실제 GPS 경로를 동일한 데이터로 취급하지 않는다.

## 2. 작업 전 필수 점검

구현에 앞서 저장소 전체를 확인하고 현재 구조를 파악한다. 아래에 적힌 파일명이나 구조가 실제 프로젝트에 없다고 가정하지 말고, 실제 파일과 호출 흐름을 추적한다.

1. 홈 화면에서 ‘바로 산책 시작하기’를 렌더링하는 컴포넌트와 클릭 이벤트를 찾는다.
2. 기존 산책 시작·진행·일시 정지·재개·종료 로직을 확인한다.
3. 현재 위치 권한, 위치 추적, 백그라운드 위치 수집, GPS 좌표 저장 로직이 있는지 확인한다.
4. 산책 기록의 데이터 모델, API, Supabase 테이블/스토리지 연계, 백엔드 저장 로직을 확인한다.
5. 산책 종료 후 기록 상세 화면 및 산책 일지·주간 달성도·통계로 연결되는 흐름을 확인한다.
6. 기존 경로 추천 기능과 자유 산책 기능이 현재 어떤 상태·API·데이터 모델을 공유하는지 확인한다.
7. Expo 및 React Native 환경에서 사용 중인 위치·백그라운드 작업 라이브러리와 버전을 확인한다.

점검 결과를 바탕으로 기존 아키텍처와 호환되는 최소 변경 방안을 세운다. 기능이 이미 구현되어 있다면 중복 구현하지 말고 결함을 수정·재사용한다.

## 3. 홈 화면 진입 구조

홈 화면에서 사용자가 두 기능의 차이를 즉시 이해하도록 구성한다.

### 3.1 바로 산책 시작하기 — 자유 산책

- 경로 추천이나 공원 선택 단계를 거치지 않고 산책을 시작한다.
- 시작 시 GPS 권한과 위치 서비스 상태를 확인한다.
- 산책 진행 화면에서 현재 위치와 실제 이동 경로를 지도에 표시한다.
- 산책 시간, 실제 이동 거리 등 측정 가능한 지표를 표시한다.
- 일시 정지, 산책 재개, 산책 종료 기능을 제공한다.
- 종료 시 실제 산책 기록을 저장하고 기록 상세/일지 작성 흐름으로 연결한다.

### 3.2 산책 경로 추천받기 — 계획 산책

- 기존 경로 추천 기능을 유지한다.
- 공원 또는 출발 위치, 희망 산책 시간·거리 등 기존에 지원하는 조건으로 추천 경로를 생성한다.
- 추천 경로의 거리, 예상 시간, 경사도, 노면 정보 등 현재 제공 가능한 정보를 보여준다.
- 추천 경로와 실제 산책 GPS 경로를 별도로 관리한다.
- 기존 추천 기능의 API 계약이나 사용자 흐름을 자유 산책 구현 때문에 임의로 변경하지 않는다.

## 4. 자유 산책 진행 화면 요구사항

화면은 기존 디자인 시스템, 색상, 폰트, 컴포넌트 규칙을 우선 재사용한다. 새로운 디자인 체계를 임의로 도입하지 않는다.

### 필수 UI

- 화면 제목: `자유 산책` 또는 기존 앱 용어 체계에 맞는 명칭
- 안내 문구: `원하는 곳으로 자유롭게 산책해 보세요.`와 같은 짧은 설명
- 지도: 현재 위치와 실제로 기록된 이동 경로 표시
- 산책 시간: 산책 시작 후 경과 시간
- 이동 거리: 유효한 GPS 좌표로 계산한 실제 이동 거리
- 걸음 수: 기존에 신뢰할 수 있는 걸음 수 측정 기능이 있는 경우에만 표시
- 주요 조작: 산책 시작, 일시 정지, 산책 재개, 산책 종료
- 상태 표시: GPS 준비 중, 위치 권한 필요, GPS 신호 약함, 기록 중, 일시 정지, 저장 중, 저장 실패 등 필요한 상태

측정할 수 없는 값은 `0`이나 임의의 추정값으로 표시하지 않는다. 예를 들어 걸음 수 기능이 없거나 데이터를 얻지 못하면 `--` 또는 기존 디자인에 맞는 미측정 상태를 표시한다.

## 5. GPS 기록 및 거리 계산

1. 산책 시작 시점부터 위치 수집을 시작하고, 좌표·수집 시각·정확도 등 현재 구현과 저장 구조에 적합한 정보를 기록한다.
2. 실제 위치 좌표는 수집 순서를 보존한다.
3. GPS 정확도가 낮거나 비정상적으로 큰 순간 이동이 감지되면 기존 정책 또는 합리적인 필터 기준을 적용한다. 임의의 좌표를 생성하거나 실제 이동 경로를 조작하지 않는다.
4. 거리 계산은 유효한 실제 좌표 간 거리를 기준으로 한다. 추천 경로의 길이를 자유 산책 거리로 대체하지 않는다.
5. 지도에는 실제 GPS 좌표를 사용해 이동선을 표시한다.
6. 위치 수집이 끊긴 구간은 근거 없이 직선 또는 추천 경로로 보정해 실제 이동처럼 표현하지 않는다. 필요하면 신호 공백을 구분해 표시한다.
7. 시간·거리 계산에서 일시 정지 구간을 포함할지 여부는 기존 앱 정책을 확인하고 일관되게 적용한다. 정책이 없다면 경과 시간과 실제 이동 기록 시간을 구분할지 검토하고 UI에 의미가 드러나게 한다.
8. 좌표가 충분하지 않거나 GPS 오류가 발생한 경우, 유효하지 않은 기록을 정상 경로처럼 저장하지 않는다.

## 6. 산책 상태 관리

산책 상태가 화면 이동이나 앱 재렌더링 때문에 초기화되지 않도록 상태 전이를 명확히 구현한다.

권장 상태 예시:

- `idle`: 산책 전
- `starting`: 권한·GPS 확인 및 시작 처리 중
- `recording`: 산책 기록 중
- `paused`: 일시 정지
- `stopping`: 종료 및 최종 계산 중
- `saving`: 기록 저장 중
- `completed`: 저장 완료
- `error`: 오류 상태

상태 이름은 기존 프로젝트 규칙에 맞춰 조정한다. 모든 상태를 반드시 별도 enum으로 만들 필요는 없지만, 불가능한 상태 전이가 발생하지 않도록 한다.

필수 검토 사항:

- 시작 버튼을 연속으로 눌러 기록이 중복 생성되지 않아야 한다.
- 일시 정지 중에는 새 좌표를 이동 경로에 계속 누적하지 않아야 한다. 필요 시 위치 구독을 중지하거나 정지 구간을 제외하는 기존 설계에 맞춘다.
- 재개 시 기존 기록에 이어서 좌표를 추가한다.
- 종료 시 위치 구독과 타이머를 정리하고 최종 거리를 계산한 뒤 저장한다.
- 화면을 벗어났다가 돌아와도 진행 중인 산책 상태가 의도치 않게 사라지지 않아야 한다.
- 진행 중인 산책이 있을 때 새 산책을 중복 시작하지 않도록 한다.
- 저장 중 중복 요청으로 같은 기록이 여러 개 생성되지 않도록 한다.

## 7. 권한, 백그라운드 및 오류 처리

- 위치 권한을 요청하기 전에 사용자에게 필요한 이유를 설명한다.
- 권한 거부 시 앱이 멈추거나 무한 로딩되지 않도록 하고, 필요한 경우 OS 설정으로 이동하는 안내를 제공한다.
- 위치 서비스가 꺼져 있으면 이를 명확히 안내한다.
- 앱이 백그라운드에 있거나 화면이 꺼져도 기록을 유지해야 한다면, 현재 Expo/React Native 구성과 OS 제약을 확인해 백그라운드 위치 권한 및 작업을 올바르게 구현한다.
- 백그라운드 기록을 지원하지 않는 상태라면 지원한다고 표시하지 않는다. Android 버전별 권한, 배터리 최적화, 스토어 정책 및 Expo 설정을 확인한다.
- GPS 신호 약화, 위치 수집 실패, 네트워크 단절, 저장 실패를 구분해 처리한다.
- 네트워크 오류 시 오프라인 임시 저장이 기존 구조에서 안전하게 가능한지 검토한다. 구현한다면 재시도·동기화·중복 방지까지 포함한다.
- 위치 정보는 민감한 데이터이므로 산책 중 필요한 범위에서만 수집하고, 기록 저장·삭제·접근 권한은 기존 개인정보 처리 원칙을 따른다.
- API 키, 토큰, 민감한 좌표 데이터를 로그에 과도하게 출력하지 않는다.

## 8. 데이터 모델과 백엔드 연계

현재 데이터 모델과 DB 스키마를 먼저 확인하고, 필요한 변경만 적용한다.

- 자유 산책 기록은 실제 GPS 경로와 실제 측정값을 보존한다.
- 추천 산책 기록이 있다면 `recommended_route`와 `actual_track`처럼 의미가 구분되는 필드 또는 기존 프로젝트의 동등한 구조를 사용한다.
- 기존 API/DB 필드와 호환되지 않는 새 필드를 임의로 만들기 전에 관련 모델, 마이그레이션, API 응답, 클라이언트 타입을 함께 확인한다.
- 필드가 없으면 기존 스키마를 무단 변경하지 말고 필요한 마이그레이션과 영향 범위를 제안한다.
- 거리·시간·좌표 데이터의 단위와 직렬화 형식을 통일한다.
- 저장 후 서버가 반환하는 기록 ID와 최종 값을 기준으로 상세 화면을 연다.
- 기록 저장 실패 시 사용자 입력과 GPS 기록이 조용히 유실되지 않도록 실패 상태와 재시도 경로를 제공한다.
- 자유 산책 기록을 기존 산책 일지, 주간 산책 달성도, 산책 통계에서 사용할 수 있는지 확인하고 기존 집계 로직과 연계한다.

## 9. 추천 경로 기능과의 분리 원칙

- 자유 산책 시작 시 경로 추천 API를 호출하거나 추천 경로 생성을 기다리지 않는다.
- 자유 산책의 이동 거리·경로는 실제 GPS 기록에서 계산한다.
- 추천 경로가 없는 자유 산책 기록을 오류 또는 미완성 추천 경로로 취급하지 않는다.
- 추천 경로가 있는 계획 산책에서도 추천 경로와 실제 GPS 트랙을 분리한다.
- 자유 산책 기능을 구현하면서 기존 공원 경계 제한이나 추천 경로 생성 로직을 우회·삭제하지 않는다.
- 자유 산책은 공원 내부에 머물도록 강제하지 않는다. 사용자가 원하는 곳으로 이동할 수 있어야 한다.
- 경로 추천 버그를 감추기 위해 자유 산책 결과를 추천 경로인 것처럼 표시하지 않는다.

## 10. 테스트 및 검증 기준

자동화 테스트와 실제 기기 검증을 모두 수행한다.

### 기능 테스트

- [ ] 경로 추천 없이 자유 산책을 시작할 수 있다.
- [ ] GPS 권한이 허용된 상태에서 실제 좌표가 기록된다.
- [ ] 좌표가 지도에 실제 이동 경로로 표시된다.
- [ ] 산책 시간과 거리가 기록에 따라 갱신된다.
- [ ] 일시 정지 중에는 거리와 좌표 누적이 의도한 정책대로 중단된다.
- [ ] 재개하면 기존 기록에 이어서 정상 기록된다.
- [ ] 종료 후 최종 거리·시간·좌표가 저장된다.
- [ ] 산책 종료 후 기록 상세 또는 일지 작성 흐름으로 이동한다.
- [ ] 주간 달성도와 통계가 자유 산책 기록을 중복 집계하지 않는다.

### 예외 및 회귀 테스트

- [ ] 위치 권한 거부 및 위치 서비스 비활성화
- [ ] GPS 신호 약화 또는 좌표 수집 중단
- [ ] 비정상적인 위치 점프 및 부정확한 좌표
- [ ] 네트워크 단절 및 기록 저장 실패
- [ ] 시작 버튼 연속 클릭 및 종료 버튼 연속 클릭
- [ ] 산책 중 화면 이동, 앱 백그라운드 전환, 화면 잠금
- [ ] 앱 재진입 시 진행 중 산책 상태 복원
- [ ] 기존 추천 경로 생성·선택·산책 기록 기능의 회귀 테스트
- [ ] 추천 경로가 없는 자유 산책 기록을 기존 데이터 처리 흐름이 정상 수용하는지 확인

### 실제 기기 검증

에뮬레이터 테스트만으로 GPS·백그라운드 동작을 확정하지 않는다. 실제 Android 기기에서 다음을 확인한다.

1. 산책 시작 후 실제로 이동하고 지도 경로와 거리 변화를 확인한다.
2. 화면을 끄고 일정 시간 이동한 뒤 기록이 유지되는지 확인한다.
3. 일시 정지 후 이동하고, 정지 구간이 거리 계산에 잘못 포함되지 않는지 확인한다.
4. GPS 신호가 약한 장소에서 상태 안내와 복구 동작을 확인한다.
5. 종료·저장 후 앱을 다시 열어 기록이 보존되는지 확인한다.

## 11. 완료 조건

다음 조건을 모두 충족한 뒤 완료로 보고한다.

1. 홈 화면에서 자유 산책과 경로 추천의 목적 및 진입점이 명확히 구분된다.
2. 자유 산책은 추천 경로 생성 없이 시작된다.
3. 실제 GPS 좌표 기반 경로·거리·시간이 기록되고 저장된다.
4. 권한, GPS 오류, 백그라운드, 저장 실패가 적절히 처리된다.
5. 저장된 기록이 기존 일지와 통계에 올바르게 연계된다.
6. 기존 경로 추천 기능에 회귀 문제가 없다.
7. 테스트 결과와 실제 기기 검증 결과가 보고서에 기록된다.

## 12. Gemini Code Assist 최종 보고 형식

구현이 끝나면 다음 내용을 보고한다.

1. **원인 및 기존 구조:** 관련 화면, 상태 관리, 위치 추적, API/DB 흐름
2. **수정 파일:** 파일별 변경 이유
3. **구현 내용:** 자유 산책 시작, GPS 추적, 거리 계산, 상태 관리, 저장, 통계 연계
4. **데이터 변경:** 스키마/API 변경 여부 및 마이그레이션
5. **테스트:** 실행한 명령, 통과·실패 항목, 실제 기기 검증 여부
6. **미해결 사항:** 백그라운드 제한 등 환경상 남은 문제와 필요한 추가 설정
7. **수동 확인 절차:** 개발자가 앱에서 재현·검증할 단계

## 13. 구현 시 금지 사항

- 실제 코드와 데이터 흐름을 확인하지 않고 파일명·API·DB 구조를 추측해 구현하지 않는다.
- 경로 추천 로직을 제거하거나 자유 산책과 섞지 않는다.
- 실제 GPS 데이터가 없는 상황에서 임의 좌표, 가짜 경로, 추정 걸음 수를 생성하지 않는다.
- 측정 불가 값을 `0`, 평지, 포장도로 등으로 잘못 표시하지 않는다.
- 백그라운드 위치 추적이 검증되지 않았는데 정상 작동한다고 보고하지 않는다.
- 기존 기능을 대규모로 리팩터링하거나 API 계약을 임의 변경하지 않는다.
- 테스트를 실행하지 않고 통과했다고 보고하지 않는다.

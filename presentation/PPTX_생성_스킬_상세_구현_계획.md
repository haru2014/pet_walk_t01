# PPTX 생성 스킬 상세 구현 계획

## 문서 목적과 범위

이 문서는 [PPTX 생성 스킬 구현 안내서](./PPTX_생성_스킬_구현_가이드.md)를 실제 작업으로 옮길 때 따라갈 구현 계획입니다. 단계마다 작업, 산출물, 확인 기준, 다음 단계로 넘어가는 조건을 정리했습니다.

이 계획은 **구현 전에 검토할 계획서**입니다. 스킬 코드나 실제 PPTX 제작 도구를 여기서 미리 설치·작성하는 것은 범위에 포함하지 않습니다. 구현 중에는 도구와 실행 환경을 먼저 확인한 뒤 선택합니다.

현재 기준으로 핵심 스킬은 Codex와 Gemini CLI에서 공용으로 찾을 수 있도록 저장소의 `.agents/skills/` 아래에 둡니다. GPT 지원은 “ChatGPT Skills”와 “OpenAI API의 Skills 실행 환경” 중 어느 쪽을 뜻하는지에 따라 배포 절차가 달라지므로, 해당 통합 단계에서 실행 환경을 확정합니다.

## 목표 산출물

구현 완료 시 아래 파일과 폴더를 갖춥니다. 필요가 확인되지 않은 빈 폴더나 스크립트는 만들지 않습니다.

```text
저장소 루트/
├─ .agents/
│  └─ skills/
│     └─ pptx-maker/
│        ├─ SKILL.md                    # 발견 조건과 핵심 제작 절차
│        ├─ references/
│        │  ├─ authoring-workflow.md    # 상세 제작·검토 절차
│        │  └─ troubleshooting.md       # 재현된 오류와 해결 방법
│        └─ scripts/                    # 자동화가 이득일 때만 추가
└─ presentation/
   ├─ README.md                         # 자료 및 산출물 폴더 안내
   ├─ design-system.md                  # 승인된 디자인 기준
   ├─ references/
   │  └─ source-log.md                  # 참고자료, 출처, 사용 범위
   ├─ templates/                        # 검토 완료된 템플릿만 보관
   ├─ examples/                         # 작은 입력 예시와 검증 결과
   ├─ evals/
   │  ├─ cases.md                       # 수동 평가 사례와 기대 결과
   │  └─ results.md                     # 실행 날짜, 결과, 발견 사항
   └─ output/                           # 요청별 최종 PPTX
```

## 단계 0. 구현 범위와 성공 조건 확정

### 작업

1. 스킬이 처리할 작업을 한 문장으로 정의합니다. 초기 제안은 “제공된 자료를 바탕으로 디자인 시스템을 적용한 편집 가능한 PPTX를 만들고, 레이아웃과 내용을 확인한다”입니다.
2. 최초 지원 대상 사용자와 PPT 종류를 정합니다. 예: 내부 보고서, 발표 자료, 교육 자료 중 우선 하나.
3. 기본 출력 형식을 `.pptx`로 둘지 확인합니다.
4. 핵심 실행 환경을 Codex와 Gemini CLI로 정하고, GPT 통합은 별도 대상 제품과 실행 환경을 정한 뒤 진행할 수 있도록 분리합니다.
5. 산출물 완료 조건을 이 문서의 “최종 완료 기준”으로 합의합니다.

### 산출물

- 구현 범위 기록: `presentation/README.md` 초안 또는 이 계획서의 변경 기록
- 지원 대상과 제외 범위
- 사용자 검토가 필요한 결정 목록

### 완료 기준

- 스킬이 만들 자료의 종류와 파일 형식이 명확합니다.
- 첫 구현에서 다루지 않을 기능이 구분되어 있습니다.
- 구현 중 사용자 선택이 필요한 디자인 기준은 선택 사항으로 명시되어 있습니다.

### 진행 게이트

요구 PPT의 주요 사용처가 여러 종류로 갈리면, 하나의 범용 스킬로 뭉치기 전에 우선 지원할 유형을 선택합니다. 유형 선택이 정해지지 않아도 저장소 조사와 도구 실험은 진행할 수 있지만, 최종 디자인 시스템은 승인 전까지 확정하지 않습니다.

## 단계 1. 저장소와 기존 PPTX 조사

### 작업

1. 루트 및 관련 하위 폴더의 `AGENTS.md`, `.gitignore`, `README.md`와 패키지 설정을 확인합니다.
2. 기존 PPTX를 목록화하고, 각각의 용도와 재사용 가능성을 확인합니다. 현재 발견된 예시는 다음과 같습니다.
   - `docs/petwalk_team_building.pptx`
   - `error/SW공학기술 적용 기본_스크럼.pptx`
3. 기존 파일을 직접 수정하지 않고 복사본 또는 읽기 전용 렌더링으로 구조, 화면 비율, 글꼴, 색상, 편집 가능성을 검사합니다.
4. 두 PPTX 가운데 하나를 디자인 기준으로 사용할지, 내용 참고로만 쓸지 확인합니다. 여러 자료의 스타일을 임의로 섞지 않습니다.
5. 기존 Node/Python 의존성과 로컬 실행 가능 도구를 기록합니다.

### 산출물

- `presentation/references/source-log.md`: 자료 이름, 위치, 참고할 항목, 사용 제한
- `presentation/README.md`: 저장소 기존 규칙, 출력 폴더 정책
- 기존 PPTX 확인 결과 및 미해결 질문

### 완료 기준

- 참고 후보와 목적이 각각 기록되어 있습니다.
- 기존 자료를 덮어쓰지 않는 작업 경로가 정해져 있습니다.
- 로컬에서 사용할 수 있는 런타임과 패키지가 확인되어 있습니다.

## 단계 2. 디자인 기준 합의 및 문서화

### 작업

1. 사용할 브랜드 자료나 기존 PPTX가 있으면 해당 자료에서 색상, 글꼴, 여백, 제목·본문 체계를 추출합니다.
2. 자료가 없거나 서로 충돌하면 선택지를 간단히 제시하고 사용자의 디자인 방향을 확정합니다.
3. `presentation/design-system.md` 초안을 작성합니다.
4. 색상값과 글꼴명만 적지 말고, 각각의 사용 위치와 대체 규칙을 적습니다.
5. 표지, 텍스트 본문, 비교·표, 차트, 마무리의 최소 레이아웃 규칙을 정의합니다.
6. 디자인 시스템 버전과 변경 기록 방식을 정합니다.

### `design-system.md`에 포함할 항목

- 적용 대상과 독자
- 기본 슬라이드 비율 및 안전 여백
- 배경·본문·강조·보조 색상과 쓰임
- 제목·본문·각주 글꼴, 크기 범위, 대체 글꼴
- 제목 줄 수와 본문 분량 기준
- 표·차트의 편집 가능성 및 색상 규칙
- 이미지·아이콘·로고의 출처와 사용 조건
- 출처 표기 규칙
- 렌더링 후 확인할 항목

### 산출물

- `presentation/design-system.md`
- 출처를 확인할 수 있는 원본 목록
- 디자인 기준 결정 사항 기록

### 완료 기준

- 기준이 실제 슬라이드에 적용할 수 있을 정도로 구체적입니다.
- 알 수 없는 로고·색상·폰트 규칙을 지어내지 않았습니다.
- 사용자의 선택이 필요한 방향은 승인 또는 보류로 표시되어 있습니다.

## 단계 3. PPTX 제작 도구 검증

### 작업

1. 저장소에 이미 있는 런타임과 패키지를 먼저 조사합니다.
2. 후보 제작 도구를 다음 기준으로 비교합니다.
   - PPTX 내보내기 지원
   - 텍스트·도형·표·차트의 편집 가능성
   - 한글 글꼴 지정 및 대체 처리
   - 로컬에서 설치·실행 가능 여부
   - Codex와 Gemini CLI의 실행 환경에서 필요한 파일에 접근 가능한지
   - 슬라이드 렌더링 및 검토 방법
3. 후보 중 최소 하나를 작은 기술 시제품으로 시험합니다. 새 의존성을 추가하기 전에 사용자에게 필요한 설치·네트워크 권한 여부를 설명합니다.
4. 시제품은 3장으로 제한합니다.
   - 표지
   - 텍스트 중심 본문
   - 표 또는 차트가 포함된 본문
5. 출력 PPTX를 열고, 가능하면 각 장을 이미지로 렌더링해 검토합니다.
6. 선택한 도구, 버전, 필요한 설치 명령, 알려진 제한을 `presentation/README.md`에 기록합니다.

### 산출물

- `presentation/examples/tool-spike.pptx` 또는 검토용 별도 작업 산출물
- 도구 비교 결과 및 선택 이유
- 반복 가능한 실행·렌더링 절차

### 완료 기준

- PPTX가 정상적으로 열립니다.
- 텍스트와 도형이 선택·수정 가능합니다.
- 데이터 표현이 필요하면 표나 차트의 실제 값도 수정 가능합니다.
- 한글 표시, 줄바꿈, 글꼴 대체, 화면 경계가 검토되었습니다.
- 선택한 도구를 지원하지 않는 환경에서 생기는 제한이 기록되었습니다.

### 진행 게이트

도구를 선택할 근거가 부족하면 의존성을 먼저 확정하지 않습니다. 시제품을 통과한 제작 방식만 다음 단계의 스킬 지침에 넣습니다.

## 단계 4. 반복 제작 절차와 검토 기준 구현

### 작업

1. 대표 입력 자료 하나를 정하고, 원하는 대상·분량·필수 내용·출처 조건을 기록합니다.
2. 슬라이드별 목적과 주요 내용을 먼저 구성한 다음 PPTX를 생성하는 절차를 정합니다.
3. 원자료에 없는 사실·숫자·출처를 추가하지 않는 규칙을 둡니다.
4. 차트와 표의 편집 요구, 이미지 출처, 글꼴 문제를 어떻게 처리할지 정합니다.
5. 렌더링, 육안 점검, 내용 대조, 수정 및 재확인 절차를 문서화합니다.
6. 반복 입력과 출력이 안정된 경우에만 스크립트 자동화를 검토합니다.

### 산출물

- `.agents/skills/pptx-maker/references/authoring-workflow.md`
- 검토 체크리스트
- 실제 대표 PPTX 초안

### 완료 기준

- 입력이 부족할 때 어떤 질문을 할지 정해져 있습니다.
- 초안 작성과 검토 단계가 분리되어 있습니다.
- 내용 정확성과 시각적 품질을 각각 검사합니다.
- 자동 검사만으로 시각 검토를 대체하지 않습니다.

## 단계 5. Codex·Gemini CLI 공용 스킬 작성

### 작업

1. `.agents/skills/pptx-maker/SKILL.md`를 만듭니다.
2. front matter에 짧고 구체적인 `name`과 `description`을 넣습니다.
3. 스킬 본문에는 사용 조건, 필요한 입력, 필수 경로, 단계, 검토 기준, 완료 시 보고 형식을 적습니다.
4. 상세한 레이아웃·도구 설명은 참조 파일로 분리합니다.
5. 특정 제품의 슬래시 명령, 전용 도구 이름, 전용 설치 경로에 의존하는 표현을 공용 본문에서 제거합니다.
6. 경로는 저장소 기준 상대 경로로 적고, 현재 작업 디렉터리가 다를 수 있으므로 루트 확인 방법을 넣습니다.
7. 실행 스크립트가 있다면 실행 전에 무슨 파일을 만들고 수정하는지, 실패 시 어디를 확인할지 지침에 적습니다.

### `SKILL.md`의 권장 목차

- 목적과 호출 조건
- 지원하지 않는 요청 또는 범위 밖인 요청
- 사용자로부터 확인할 입력
- 사용할 디자인 기준 파일
- 제작 순서
- PPTX 렌더링과 검토 순서
- 실패 시 대응
- 결과물 위치와 최종 보고 항목

### 산출물

- `.agents/skills/pptx-maker/SKILL.md`
- 필요할 때만 참조 파일과 스크립트

### 완료 기준

- 메타데이터의 이름과 설명으로 스킬의 쓰임을 구분할 수 있습니다.
- 본문에서 디자인 시스템과 제작 절차를 찾을 수 있습니다.
- 저장소 외 경로, 특정 사용자 홈 경로, 설치되지 않은 도구를 전제로 하지 않습니다.
- 스킬을 호출하지 않은 일반 문서 작업과 호출해야 할 PPT 작업이 구별됩니다.

## 단계 6. 대표 PPT 생성 및 시각·내용 검증

### 작업

1. 단계 4에서 정한 대표 입력으로 초안 PPTX를 만듭니다.
2. 렌더링 가능한 환경에서 전체 슬라이드를 이미지로 내보냅니다.
3. 각 슬라이드를 앞에서부터 확인하고 글자 잘림, 줄바꿈, 정렬, 대비, 표·차트의 범례를 기록합니다.
4. 텍스트와 숫자를 원자료와 대조합니다.
5. PPTX를 다시 열어 텍스트·도형·표·차트의 수정 가능성을 시험합니다.
6. 발견한 문제를 수정하고, 수정 후 전체 장을 다시 렌더링해 회귀 여부를 확인합니다.
7. 최종 산출물과 임시 렌더링 파일의 위치를 분리합니다.

### 산출물

- 검토 완료된 대표 PPTX
- 렌더링 미리보기 또는 검토 기록
- 결함 목록과 해결 결과

### 완료 기준

- 모든 슬라이드에서 제목·본문·도형이 겹치거나 잘리지 않습니다.
- 숫자, 단위, 표·차트 데이터가 입력 자료와 일치합니다.
- 글꼴 대체가 발생한 경우에도 읽을 수 있습니다.
- 요청된 요소를 편집할 수 있습니다.
- 해결하지 못한 문제는 숨기지 않고 목록에 남깁니다.

## 단계 7. 반복 평가 사례와 회귀 확인 구성

### 작업

1. `presentation/evals/cases.md`에 스킬이 처리할 대표 요청을 기록합니다.
2. 다음 요청 유형을 포함합니다.
   - 스킬을 명시해 부르는 요청
   - 자연어 PPT 생성 요청
   - 원자료가 충분한 요청
   - 자료 또는 출처가 부족한 요청
   - 긴 제목·표·차트 등 레이아웃 부담이 있는 요청
   - PPT 제작과 무관한 인접 요청(스킬이 과하게 호출되지 않는지 확인)
3. 각 사례에 기대하는 파일, 금지 행동, 시각 검토 항목을 적습니다.
4. 스킬 변경 시 같은 입력으로 다시 실행하고 `presentation/evals/results.md`에 결과와 변경점을 기록합니다.
5. 자동 평가를 만들 경우 실제로 반복되는 검사만 자동화합니다. 파일 존재, 슬라이드 수, 필수 출처 확인은 자동화 후보이며, 시각 품질은 사람 검토를 유지합니다.

### 산출물

- `presentation/evals/cases.md`
- `presentation/evals/results.md`
- 필요가 확인된 평가 스크립트

### 완료 기준

- 스킬을 못 찾는 문제, 과하게 호출하는 문제, 제작 품질 문제를 각각 확인할 수 있습니다.
- 모든 실패 사례에는 재현 절차와 기대 결과가 있습니다.
- 스킬 수정 전후 결과를 비교할 수 있습니다.

## 단계 8. GPT 제품별 배포 선택

### 먼저 선택할 것

“GPT에서 사용”이 아래 중 무엇인지 정합니다.

1. **ChatGPT Skills 기능:** 스킬 폴더를 업로드 가능한 패키지로 묶고, 계정·워크스페이스에서 지원하는지 확인합니다.
2. **OpenAI API의 Skills 실행 환경:** API 문서에 맞게 스킬 파일을 업로드하거나 실행 환경에 포함합니다.
3. **사용자 정의 GPT의 지침/파일:** 플랫폼이 제공하는 지침과 지식 파일 기능에 맞게 내용을 옮깁니다. Codex의 로컬 경로와 스크립트가 자동으로 이어진다고 가정하지 않습니다.

### 작업

1. 대상 제품과 실제 사용할 실행 환경을 확정합니다.
2. `presentation/design-system.md`가 공유 패키지 밖에 있는 경우 패키지에 포함하거나, 각 환경에서 접근 가능한 위치로 복사하는 방식을 정합니다.
3. 스크립트 사용 시 해당 환경에 런타임, 패키지, 파일 시스템 쓰기 권한이 있는지 확인합니다.
4. 제품별 패키지에 동일한 핵심 지침과 검증 기준이 들어 있는지 대조합니다.
5. 해당 제품에서 직접 시험하고, 실행할 수 없는 기능은 제한 사항으로 명시합니다.

### 완료 기준

- 타깃 GPT 제품과 배포 방식을 문서에 명시했습니다.
- 디자인 자료와 필요한 스크립트가 실행 환경 안에서 실제 접근 가능합니다.
- 제품별 호출·저장·파일 생성·렌더링 과정을 따로 확인했습니다.
- 지원되지 않는 기능을 “호환”이라고 표현하지 않습니다.

## 단계 9. 문서화와 유지관리

### 작업

1. `presentation/README.md`에 폴더별 목적, 실행 방법, 출력 위치, 검토 방법을 적습니다.
2. 사용자가 최종 PPTX를 요청할 때 출력 위치와 파일명 충돌 처리 규칙을 둡니다.
3. 임시 파일을 `output/`에 두지 않도록 합니다.
4. 외부 이미지·폰트·템플릿의 출처와 사용 조건을 유지합니다.
5. 도구·런타임 버전을 올릴 때는 대표 평가 사례를 다시 실행합니다.
6. 실패가 반복되면 지침을 늘리기 전에 원인과 재현 사례를 기록하고, 필요한 최소 변경을 적용합니다.

### 완료 기준

- 새 사용자가 README만 읽고 대표 요청을 실행할 수 있습니다.
- 스킬과 디자인 시스템의 변경 이력을 추적할 수 있습니다.
- 실패 원인과 알려진 한계가 기록되어 있습니다.
